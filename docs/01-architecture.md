## 0. 先把话说明白：原厂 App 已经死了，但它还没被埋

`com.phicomm.speaker.device` 这个 App 的云端（云知声 NLU + 斐讯后端）已经下线。
它现在里面还活着的只有三样东西：

1. **本地唤醒**（「小讯小讯」，离线跑）
2. **本地 ASR**（语音转文字，离线跑）
3. **音频采集**（四麦，走 ALSA 直开）

**但原厂代码里有三道闸门**（`patch_bindgate.py` 拆的就是这个）：
「未绑定 / 无网络 / 待升级」——全都要连斐讯服务器，而服务器已死，所以闸门永远不放行。
**这就是为什么原厂机现在叫不动。**

而语义层（听懂之后干什么）原本全在云上，现在空的。

> 所以我们面对的不是「优化一个能用的 App」，而是「**给一具还在呼吸的躯壳接上新的脑子**」。

## 1. 架构定稿

```
┌──────────────────────────────────────────────────────────────┐
│  L3  控制面（电脑 / NAS / 手机浏览器）                          │
│      配置、日志、部署、升级                                      │
│      不装在音箱上 —— 内存只有 5.7MB 空闲，装不起                 │
└──────────────────────────────────────────────────────────────┘
                    ▲ HTTP（局域网）
┌──────────────────────────────────────────────────────────────┐
│  L2  业务 App（我们自己的包，如 com.r1.brain）                   │
│      - 全部业务逻辑：对话、意图、音乐、消息                       │
│      - 自己的配置（SharedPreferences）                          │
│      - ❌ 不碰麦克风：钉死结论——麦克风被原厂链独占，             │
│        详见第 6 节（实测：能初始化、能 start，但 read 永远阻塞）   │
│      - 要底层能力时，通过广播/socket 请求 L1                     │
│      ✅ 随时 pm uninstall，不影响原厂                            │
└──────────────────────────────────────────────────────────────┘
                    ▲ Binder / 广播 / 本地 socket
┌──────────────────────────────────────────────────────────────┐
│  L1  桥（顶替 com.phicomm.speaker.device 的薄壳，~几百行）        │
│      只保留三件事：                                             │
│      ① 原厂唤醒 + ASR（云知声 SDK 必须在包里）                    │
│      ② 灯环（ISysPrivate 4096 消息）                            │
│      ③ 系统模式 setSysMode                                      │
│      把 ①②③ 的结果转发给 L2，自己不做任何业务判断                 │
└──────────────────────────────────────────────────────────────┘
```

### 为什么是这个形状

| 约束 | 怎么解 |
|---|---|
| 内存 5.7MB | L1 极薄，L2 单进程，L3 不在设备上 |
| 原厂唤醒只有那个包里有 | 把唤醒留在 L1，只把「听到了什么」转出去 |
| 灯环要 `ISysPrivate` | 只有 L1 有身份，所以灯控命令必须过 L1 |
| 业务要能天天改 | 全在 L2，改完 `pm install` 就行，**不用重新 Janus 打包** |
| 怕搞坏 | L1 只做转发 + 原厂已有能力，不加新逻辑；坏了 `pm uninstall` 回 `/system/app/Unisound` |

## 2. 关键技术决定

### 2.1 控制面：独立端口 + 独立协议 + 必须有鉴权

原厂本来没有对外 HTTP 服务；我们也不去复用任何历史页面（那些东西随旧包一起消失了，
需要时查 `archive/`）。

**L2 自己在 8686 起一个 HTTP 服务**，接口与鉴权见 `docs/08-http-api.md`：
默认开放，用户设置令牌后强制校验；静态页面公开，方便先打开页面再补令牌。

### 2.2 四麦：算法在 HAL 里，但麦克风被原厂链独占

`audio.primary.rk30board.so`（mediaserver 加载）确实链了
`libuni4michal.so` / `libUniMicArray.so`，导入了 `uni_4mic_pcm_open/read`。
也就是说**四麦波束成形不需要特权域**。

**但是**（2026-10-29 实测补正）：
`/proc/asound/card1/pcm0c/sub0/info` 显示 `subdevices_count: 1`、`subdevices_avail: 0`，
原厂唤醒链 100% 占着这一路采集。任何其它 App 的 `AudioRecord` 能初始化、
能 `startRecording`，但 `read()` 永远阻塞、拿不到采样。
停掉原厂链后立刻能录到真实数据。

⇒ **结论不是「不用顶替」，而是「拿麦这件事根本轮不到 L2」**（见第 6 节）。
四麦算法确实不用我们实现，但采集权必须留在 L1。

### 2.3 「顶替」只能锁死包名

Janus 的机制决定：**包名必须是被顶替的那个**（manifest 改了会让 v1 摘要失配）。
所以 L1 的包名只能是 `com.phicomm.speaker.device`，没有别的选择。

这也是为什么必须分成 L1 + L2 两层：
**L1 因为要顶替，天然不可自由迭代；L2 没有这个约束，想怎么改怎么改。**

### 2.4 部署不依赖 ADB

```
改代码 → 编译 → 放 L3 的 Web 服务器 → 音箱上点「检查更新」下载安装
```

这样**即使哪天 5555 被关了，也还能升级自己的 App**。
adb 只是开发期的快车道。

## 3. 分期实施

### 第一期：只做 L2（零风险）

**目标：证明「业务逻辑能跑通」——因为麦克风碰不到，这一期用文本输入驱动。**

- [ ] 起项目（Java 8，minSdk 22，AOSP armv7 模拟器可跑）
- [ ] 定一个调试入口：`adb shell am broadcast` 发一段文本 → App 当作「听到了这句话」处理
- [ ] 接 LLM（OpenAI 兼容），跑通「文本进 → 文本出」
- [ ] TTS 播报（先用系统 TTS，验证音频输出通路）
- [ ] 意图路由（音乐 / 天气 / 闲聊 / 定时）
- [ ] 音乐播放（先接 Navidrome 这种最标准的）
- [ ] 自己的配置界面（跑在 L3 网页上，App 里只留调试页）

**这一期完全不碰设备能力，装坏了 `pm uninstall` 就没了。**
90% 的工作量在这一层，而它是零风险的 —— 所以先做完它。

### 第二期：L1 桥（一次性，做完很少改）

- [ ] 本地 PoC 先做 Janus 包（在 PC 上验，不碰设备）
- [ ] 上机顶替 `com.phicomm.speaker.device`
- [ ] 拆三道闸门（未绑定 / 无网络 / 待升级）
- [ ] 打通 L1 ↔ L2 的广播协议
- [ ] 灯环 / 系统模式

### 第三期：合并体验

- [ ] L1 唤醒 → L2 大脑 → L1 播报/灯效
- [ ] 端到端延迟优化（目标：说完话 2 秒内开口）

## 4. 还没定、需要你拍板的

| 问题 | 选项 | 影响 |
|---|---|---|
| **LLM 用哪个** | 智谱 GLM / 豆包 / DeepSeek / 本地 Ollama | 决定延迟和成本；实测 GLM-4.5-Flash 0.5~1 秒，GLM-4.7 要 27~68 秒 |
| **TTS 用谁的** | 原厂云知声 TTS / 云端 TTS（豆包音色） | 原厂的能用但音色机械；云端要网络 |
| **音乐源** | Navidrome / 网易云 / QQ / 本地 | 决定要不要在 NAS 上多跑服务 |
| **要不要接 HA** | 要 / 不要 | 要的话所有设备控制都能白嫖 HA |
| **L3 跑在哪台机器** | 你的 NAS / 这台 PC / 树莓派 | 决定部署方式 |

## 5. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| L2 内存不够，被系统杀 | 中 | App 反复重启 | **清理后空闲约 25MB**，要狠省内存；保活先靠广播 |
| L1 顶替失败 | 低（本机现役包就是 Janus，已证明可行） | 语音助手没了 | `pm uninstall` 回 `/system/app/Unisound` |
| 改 L1 时把语音链弄坏 | 中 | 叫不动 | L1 底包固定为 `l1/vendor/Unisound_original.apk`（SHA-256 钉住）；改动前先留底，坏了 `pm uninstall` 回原厂 |
| IP 变了找不到设备 | 高 | 控制面失联 | 路由器绑 MAC `<音箱MAC>` |
| adbd 反复挂死 | **高（已发生两次）** | 无法远程操作 | 断电重启；长期靠 L3 网页下载安装绕开 adb |
| 麦克风被原厂链独占 | **已确认** | L2 采不到音频 | 已据此定稿架构（第 6 节） |

## 6. 麦克风归属：已测出结果，架构据此定稿

### 6.1 结论

> **四麦采集设备只有一路 substream，被原厂语音链 100% 独占。**
> 唤醒链在跑时，任何其它 App 能初始化 `AudioRecord`、能 `startRecording`，
> 但 **`read()` 永远阻塞、拿不到一个采样**。
> 把原厂链停掉，同一个 App 1.2 秒就录到 16000 个真实采样。

完整数据见 `archive/evidence-mic-exclusivity.md`。三条硬证据：

```
/proc/asound/card1/pcm0c/sub0/info
  subdevices_count: 1      ← 硬件层只有一路
  subdevices_avail: 0      ← 被占

被占时（探针 com.r1.probe）:
  MIC state=1 (INITIALIZED)
  MIC recordingState=3 (RECORDING)
  → 卡死在 read()，0 采样

停掉原厂链后（同一份代码）:
  MIC RESULT samples=16000 reads=10 maxAbs=79 costMs=1189 -> GOT_AUDIO
  VOICE_RECOGNITION RESULT samples=16000 maxAbs=70 -> GOT_AUDIO
```

**不是权限问题，不是 SELinux 问题，不是硬件问题 —— 是 ALSA 独占。**

### 6.2 于是架构只剩两条路

| | **A1 顶替原厂包**（选这条） | A2 停用原厂链，自己做唤醒 |
|---|---|---|
| 麦克风 | 原厂链继续拿着，我们**在同一个进程里**接它的识别结果 | 我们独占，原厂链必须停 |
| 唤醒词 | 保留「小讯小讯」，出厂调好的 | 自己实现（Porcupine / Snowboy / 自训） |
| 四麦波束 | 原样沿用 | 走 AudioRecord → HAL（已证明能录，但算法效果待调） |
| 内存 | 不额外占 | **清理后空闲约 25MB，再跑唤醒引擎风险仍高** |
| 是否要 Janus | 要 | 不要 |
| 迭代成本 | 改桥就要重新打包顶替 | 普通 `pm install`，想怎么改怎么改 |
| 语音质量 | 与现在一致 | 需要重新调，大概率更差 |

**选 A1。** 理由只有一条但足够：**唤醒质量是这类产品的命门**，
A1 能沿用出厂调好的本地唤醒 + 本地 ASR，A2 要从零调，在 490MB 内存的机器上还未必跑得动。

### 6.3 定稿架构（A1）

```
┌────────────────────────────────────────────────────────────────┐
│ L3  控制面（PC / NAS / 手机浏览器）                               │
│     配置、日志、部署、升级 —— 不装在音箱上                         │
└────────────────────────────────────────────────────────────────┘
                     ▲ HTTP（带鉴权）
┌────────────────────────────────────────────────────────────────┐
│ L2  业务 App（自己的包名，如 com.r1.brain）                        │
│     ★ 全部业务逻辑都在这里：                                      │
│       对话 / LLM / 意图 / 音乐 / 消息 / HA / 天气 / 记忆           │
│     ★ 运维中枢与空中 OTA 升级（基于 127.0.0.1:5555 回环特权）       │
│     ★ 纯流式低内存 I/O（8KB 缓冲直写，杜绝 512MB RAM OOM）         │
│     ★ 自己的配置（SharedPreferences）                             │
│     ★ 不碰麦克风（碰不到，也不需要）                               │
│     ★ 普通 APK —— 支持 Web 端空中 OTA 一键自升级，免插电脑          │
└────────────────────────────────────────────────────────────────┘
                     ▲ 本地广播 / socket（文本 + 指令）
┌────────────────────────────────────────────────────────────────┐
│ L1  桥（Janus 顶替 com.phicomm.speaker.device，保持极薄）          │
│     ① 原厂唤醒 + 本地 ASR 继续跑（唯一能拿麦的进程）               │
│     ② 拿到识别文本 → 转给 L2                                     │
│     ③ 收 L2 回的文本 → 用原厂 TTS 播出去                         │
│     ④ 灯环 / 系统模式（ISysPrivate，只有这个身份能调）             │
│     ⑤ 拆掉原厂三道闸门（未绑定/无网络/待升级）                    │
│     ⚠️ 只在「桥协议」变化时才需要重新打包                          │
└────────────────────────────────────────────────────────────────┘
```

### 6.4 这个分法的好处

| 关注点 | 结果 |
|---|---|
| 想天天改业务 | 全在 L2，`pm install` 就行，**不用碰 Janus** |
| 内存只有约 25MB 空闲（清理后） | L1 只有转发逻辑，L2 单进程，L3 不在设备上 |
| 怕搞坏 | L1 只用原厂已有能力，不加新逻辑；坏了 `pm uninstall` 回 `/system/app/Unisound` |
| 唤醒质量 | 沿用出厂的，不退化 |
| 灯环 | 只有 L1 能调，但这是一条消息的事，不需要频繁改 |

### 6.5 L1 ↔ L2 的接口（唯一需要一次定死的协议）

```
L1 → L2   ASR_RESULT   { text, sessionId, timestamp }
L1 → L2   WAKEUP       { sessionId }             唤醒瞬间（可选，用于打断）
L1 → L2   KEY_EVENT    { click/long/double }

L2 → L1   SPEAK        { text }                  让原厂 TTS 播
L2 → L1   LIGHT        { index(1-24), on/off }   或 { special: dormant/loading/netlost }
L2 → L1   SYS_MODE     { mode }
L2 → L1   STOP         { sessionId }             打断当前播报
```

用**本地 socket（抽象命名空间）**最省事，广播（Broadcast）也行但 Android 5.1 上
隐式广播限制少、反而更好用。**建议先做广播，需要低延迟时再换 socket。**

> 注意：L1 和 L2 不是同一个 uid，所以共享文件要走 `/data/local/tmp` 或 ContentProvider。
> 广播是跨 uid 最轻的方式。

### 6.6 一个必须注意的坑

`ApiHelper.interceptTTS` 是 TTS 回调线程，**在那里做任何同步等待都会持有 audio 管线锁，
导致整机卡死**（早期方案踩过这个坑，症状是叫不醒、没声音、只能断电）。

⇒ L1 里**绝对不能**在 TTS 回调里等任何回包。
正确做法：收到 ASR 结果 → 立刻 return → 异步等 L2 → 拿到结果后再调 `ctx.playTTS()`。

## 7. 最终实施路线

```
第一步  L2 单机跑通（不接 L1，零风险）
        - 用文本输入调试（adb 广播触发，或自己写个测试入口）
        - LLM / 音乐 / 意图全跑通
        - 证明「业务逻辑没问题」

第二步  L1 桥（一次性的，做完就很少改）
        - 本地 PoC 先做 Janus 包（在 PC 上验，不碰设备）
        - 上机：换掉 com.phicomm.speaker.device
        - 打通 L1 ↔ L2

第三步  合并验收
        - 唤醒 → L2 → 回复 → TTS
        - 灯环、按键
```

**第一步完全不碰设备能力，纯 APP 开发，随便折腾。**
这也是为什么值得先把 L2 单独做完 —— 90% 的工作量在这一层，而它是零风险的。
