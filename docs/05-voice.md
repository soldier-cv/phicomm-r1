# 语音播报与对话模式设计

> 依据：2026-10-29 对 `http://<服务IP>:8317/v1/audio/speech` 的实测（本文所有数字都是跑出来的）。
> 目标：一套引擎同时支撑「一次性播报」和「持续对话（打电话模式）」。

---

## 一、先纠正一个参数

```
POST {"model":"x/grok-tts", ...}
→ 400: Model x/grok-tts is not supported. Use grok-tts.
```

**正确的 model 是 `grok-tts`，不带 `x/` 前缀。**

可用参数：

| 参数 | 值 | 说明 |
|---|---|---|
| `model` | **`grok-tts`** | 带前缀会 400 |
| `voice` | `alloy` / `echo` / `fable` / `onyx` / `nova` / `shimmer` | OpenAI 那六种 |
| `input` | ≤ **10,000** 字 | |
| `speed` | **0.7 ~ 1.5** | 实测生效；超出范围会被拒 |
| `response_format` | `mp3`（默认）/ `wav` / `pcm` | `opus`/`aac`/`flac` → 400 |

三种格式的实际产出（实测）：

| 格式 | 内容 | 同一段长文本的体积 |
|---|---|---:|
| `mp3` | MPEG III，128 kbps / 24 kHz / 单声道 | 231 KB |
| `wav` | RIFF WAVE，PCM 16bit / 24 kHz / 单声道 | ≈706 KB |
| `pcm` | 裸 PCM，无文件头 | ≈706 KB |

**体积差 3 倍**（mp3 vs pcm）。局域网无所谓，但长文本（1 万字上限）用 pcm 会到 ~20 MB。

## 二、实测数据（这决定后面所有设计）

### 2.1 单次合成：耗时与文本长度的关系

| 文本长度 | 返回体积 | 合成耗时 | 折算音频时长 | 合成/实时比 |
|---:|---:|---:|---:|---:|
| 22 字 | 51,840 B | **1.64 s** | ≈3.2 s | 0.51× |
| 60 字 | 139,008 B | **3.06 s** | ≈8.7 s | 0.35× |
| 180 字 | 395,136 B | **3.14 s** | ≈24.7 s | 0.13× |

> 音频体积换算依据：128 kbps = 16 KB/s。
> **关键结论：合成比实时快得多，长文本几乎不增加等待。**

### 2.2 并发能力

3 个短句：

```
串行：1.72 + 1.68 + 1.53 = 4.99 s
并发：墙钟 3.05 s（各自 1.43 / 1.69 / 2.33 s）
```

**并发确实有效，但收益不是线性的（约 1.6×）**——服务端有争抢。

### 2.3 首句延迟的"地板"

即使只有 22 个字，也要 **1.6 秒**。
这是**固定开销**（连接 + 模型预热），短文本压不下去。

> **所以对话模式的首音延迟下限 ≈ 1.6 s（TTS） + 0.5~1.0 s（LLM） ≈ 2.2~2.6 s。**
> 想更快只有一条路：**预合成 + 缓存常用语**。

### 2.4 ⚠️ 服务端不是流式的（这条改变了格式选择）

同一段长文本，分别要 mp3 和 pcm，观察首字节时间（TTFB）：

| 格式 | TTFB | 总耗时 | 体积 |
|---|---:|---:|---:|
| mp3 | **3.22 s** | 3.26 s | 231 KB |
| pcm | **3.72 s** | 3.88 s | 706 KB |

**TTFB ≈ 总耗时** —— 虽然响应头是 `Transfer-Encoding: chunked`，
但数据是**全部合成完之后一次性发出来的**，不是边生成边推。

**这条推翻了"用 pcm 流式播放能降低首音延迟"的想法。**
既然拿不到增量数据，那 pcm 相比 mp3 只剩两个差别：

| 差别 | 值不值得 |
|---|---|
| 省掉 MP3 解码 | ❌ 不值得 —— R1 是完整 Android，`MediaPlayer` 原生解 mp3，解码不是瓶颈 |
| 句间无缝衔接（PCM 可拼成一条连续流） | ✅ **这个有价值**，见 4.5 |

> 顺带纠正一个常见假设：**"嵌入式芯片没有 MP3 解码器"对 R1 不成立**。
> 它不是 ESP32，是 Android 5.1 + mediaserver，mp3 解码是系统自带能力。

## 三、三种使用场景（这是本文的核心）

| 模式 | 长什么样 | 依赖 | 首音延迟目标 |
|---|---|---|---|
| **M1 单次播报** | 问一句答一句，说完就结束 | **L2 独立** | ≤ 3 s |
| **M2 连续对话（半双工）** | 说完自动进入聆听，像打电话但轮流说 | **需 L1**（麦克风） | ≤ 2.5 s |
| **M3 全双工（真·打电话）** | 边说边听，随时打断 | **需 L1 + AEC** | ≤ 1.5 s |

### 3.1 为什么 M2/M3 必须要 L1

麦克风被原厂语音链 100% 独占（`archive/evidence-mic-exclusivity.md` 实测）。
L2 连一个采样都拿不到。所以：

```
M1：L2 自己说话，不需要听 → 可行
M2：需要"听" → 只能靠 L1 把 ASR 文本转过来
M3：需要"边说边听" → L1 不但要给文本，还要处理 AEC（否则音箱自己的声音会被当成用户说话）
```

**结论：M1 现在就能做；M2 等 L1；M3 还要额外解决 AEC。**

### 3.2 关于 AEC（回声消除）

- 原厂包里有 `libaec.so`，四麦 HAL 里也有 AEC 参数（`aec_enlarge_4mic`）
- 但那是**原厂链在采音时**做的，我们的 L2 用不上
- M3 要真做，得在 L1 里复用原厂的 AEC 通路

> **本期不做 M3。** 先把 M1 做扎实，M2 等 L1，M3 视效果再定。

## 四、播报引擎设计（M1 和 M2 共用）

### 4.1 管线

```
回答文本
   │
   ├─ ① 分句（按 。！？；\n）
   │     每句 ≤ 60 字，超了按逗号再切
   │
   ├─ ② 首句立即请求（不等其它）
   │
   ├─ ③ 其余句子并发请求（并发度 2~3）
   │
   ├─ ④ 有序队列播放（谁先到不重要，必须按顺序播）
   │
   └─ ⑤ 播第 N 句时，第 N+1 句已在合成 → 无缝衔接
```

### 4.2 分句规则

| 规则 | 值 | 理由 |
|---|---|---|
| 切分符 | `。！？；` 和换行 | 语义完整 |
| 单句上限 | 60 字 | 实测 60 字 ≈3 s 合成，可接受 |
| 超长再切 | 按 `，、` | |
| 首句目标 | ≤ 20 字 | 首句越短，开口越快 |
| 最少并发 | 2 句以上才并发 | 单句没必要 |

### 4.3 并发与顺序

```java
// 伪代码
List<String> parts = split(text);
Future<byte[]> first = pool.submit(synth(parts.get(0)));
List<Future<byte[]>> rest = 并发提交 parts[1..n]（最多 3 个同时在跑）

play(await(first));                    // 首句先播
for (Future<byte[]> f : rest) {
    play(await(f));                    // 严格按顺序
}
```

**为什么要"有序队列"**：并发合成完成的顺序是乱的，但播报必须按句子顺序。

### 4.4 打断

```
新播报到来 或 用户按键/唤醒
   ↓
stop()：MediaPlayer.stop()
       清空待播队列
       cancel 未完成的 Future
       删临时文件
   ↓
回到 idle
```

**打断要彻底**：不 cancel 的话，后面的句子还会陆续合成完、占内存、并可能被误播。

### 4.5 播放实现：mp3 为主，pcm 留给"无缝"

| 方案 | 用在哪 | 理由 |
|---|---|---|
| **mp3 + `MediaPlayer`** | ✅ **默认**，M1 全部场景 | 体积小、系统原生解码、代码最少 |
| **pcm + `AudioTrack`** | 可选，二期 | 多句拼接时**没有句间空隙**（MediaPlayer 每换一个文件会有 100~200ms 断点） |

**为什么默认不用 pcm**：实测服务端不流式，pcm 拿不到"边下边播"的好处，
只多出 3 倍体积和一份 AudioTrack 缓冲管理代码。

**什么时候切 pcm**：如果实测发现句间空隙明显（>200ms）影响听感，
就把同一轮回答的多个 mp3 先全部合成好、解码成 PCM、拼成一条流喂 `AudioTrack`。
这条路留作二期优化，接口预留 `AudioSink` 抽象即可。

### 4.6 缓存

| 层 | 内容 | 命中效果 |
|---|---|---|
| **L1 预置短语** | "好的"、"稍等"、"我在听"、"网络不太好" | 0.15 s 出声 |
| **L2 LRU** | 按 `md5(text+voice+speed)`，30 条 | 0.15 s 出声 |

> 预置短语是**唯一能把首音压到 1 秒内**的手段，对话模式必须用。

## 五、M2 连续对话的状态机

```
         ┌──────────────────────────────────────────┐
         │                                          │
   待唤醒 ──唤醒──► 聆听 ──ASR 出结果──► 思考 ──LLM──► 播报
                      ▲                              │
                      │                              │
                      └──── 播完自动回到聆听 ◄────────┘
                      
   任意时刻：按键 / 唤醒词 → 打断播报 → 回到聆听
   30 秒无语音 → 播"好的，有事再叫我" → 退出到待唤醒
```

| 状态 | 进入条件 | 退出条件 | 音箱表现 |
|---|---|---|---|
| 待唤醒 | 空闲 | 唤醒词 | 灯灭 |
| 聆听 | 唤醒 / 上一轮播完 | ASR 出结果 / 超时 5s | 灯呼吸 |
| 思考 | 收到 ASR 文本 | LLM 返回 / 超时 8s | 灯转圈 |
| 播报 | 拿到回答 | 播完 / 被打断 | 灯随音量跳 |

**超时策略**

| 环节 | 超时 | 超时后 |
|---|---|---|
| 聆听无语音 | 5 s | 回待唤醒（不播任何话，避免吵） |
| LLM | 8 s | 播"我这会儿有点慢，再说一次？" |
| 整轮无交互 | 30 s | 退出对话模式 |

> **M2 的"聆听"和"播报"是互斥的**（半双工）。这就是它不需要 AEC 的原因，
> 也是它和 M3 的本质区别。

## 六、接口设计

### 6.1 内部（L2）

```java
public interface SpeechEngine {
    /** 一次性播报：分句 + 并发 + 有序播放 */
    void say(String text, Options opt, Callback cb);

    /** 立刻停止，清空队列，取消未完成的合成 */
    void stop();

    /** idle | synthesizing | playing | error:xxx */
    String status();
}

public static class Options {
    String voice = "nova";
    float speed = 1.0f;
    boolean interrupt = true;     // 新播报是否打断旧的
    boolean useCache = true;
}
```

### 6.2 HTTP（网页 / 调试）

```
POST /api/v1/tts          {"text":"...","voice":"nova","interrupt":true}
                          → {"ok":true,"sentences":2,"firstAudioMs":1650}
POST /api/v1/tts/stop     → {"ok":true}
GET  /api/v1/tts/status   → {"state":"playing","index":1,"total":2}
GET  /api/v1/tts/voices   → ["alloy","echo","fable","onyx","nova","shimmer"]
```

`firstAudioMs` 这个字段很重要——**它是衡量体验的唯一指标**，每次调用都记下来。

## 七、延迟预算（三档）

| 场景 | LLM | 首句合成 | 播放启动 | **首音** |
|---|---:|---:|---:|---:|
| 缓存命中（预置短语） | — | 0 | 0.15 s | **0.15 s** |
| 缓存命中（整句） | — | 0 | 0.15 s | **0.15 s** |
| 短回答（单句 20 字） | 0.8 s | 1.6 s | 0.15 s | **2.55 s** |
| 长回答（分句，首句 15 字） | 0.8 s | 1.5 s | 0.15 s | **2.45 s** |

**优化路径（按性价比）**

1. ✅ 预置短语缓存（0.15 s）—— 对话模式开场白必用
2. ✅ 首句切短（≤20 字）
3. ⬜ 让 LLM 先吐第一句（流式 LLM，二期）
4. ⬜ 本地 TTS 换成更快的模型（看服务端）

## 八、资源与清理

## 九、验证方案（人不在跟前也能判）

| # | 证据 | 判据 |
|---|---|---|
| 1 | `MediaPlayer.onPrepared` | 日志有 `duration=` 且 > 0 |
| 2 | **`START` → `COMPLETED` 的时间差** | 与 `duration` 吻合（误差 < 500ms） |
| 3 | `firstAudioMs` | 网页上能看到实际值 |
| 4 | ~~`/proc/asound/card2/pcm0p/sub0/status`~~ | ⚠️ **2026-10-29 实测作废**，见下 |

> ⚠️ **`card2/pcm0p` 的 RUNNING 不能当判据（实测推翻）。**
> AudioFlinger 常驻持有该 substream，**没放任何声音时 card0（HDMI）和 card2（AK7755）
> 也同时显示 RUNNING**。第一次 `tinyplay` 测试就是被这个现象误导的 —— 当时以为
> 「RUNNING 6 秒 = 播出去了」，实际上它跟播放无关。
>
> 现在能用的客观判据只有 `onPrepared` 的 duration 和 `START→COMPLETED` 的时长吻合：
> 2026-10-29 用 `tools/play-probe` 实测 `duration=4148ms`、`START→COMPLETED=4168ms`，
> 同时人耳确认听到声音 —— 这条链路是可信的。
>
> 出声本身最终仍要靠耳朵确认一次（codec/功放有没有真的驱动喇叭，读寄存器看不出来）。

## 十、风险

| 风险 | 概率 | 应对 |
|---|---|---|
| `MediaPlayer` 不出声 | 低（先按能出声推进） | 改 `AudioTrack` + MP3 解码库；或交给 L1 |
| 首音 2.5 s 太慢 | 中 | 预置短语 + 首句切短；M2 里先播"嗯，我想想" |
| 并发把服务端压垮 | 中 | 并发度锁 2~3，实测 3 并发只快 1.6× |
| 长文本一次播 25 秒没人愿意等 | 高 | **必须分句**，播第一句时后面还在合成 |
| 与蓝牙/DLNA 抢音频 | 中 | 申请音频焦点 |
| M2 半双工仍会串音 | 低 | 播报时不听；靠"播完再开麦"错开 |

## 十一、实施顺序

| 阶段 | 做什么 | 依赖 |
|---|---|---|
| **A** | `SpeechEngine` 单句版（不分句）+ 缓存 + 验证脚本 | 无 |
| **B** | 分句 + 并发 + 有序队列 | A |
| **C** | 接进对话链路（回答完自动播）+ 网页试听 | B |
| **D** | 预置短语缓存 + 打断 | C |
| **E** | M2 连续对话 | **需 L1** |
| **F** | M3 全双工 | L1 + AEC |

**A 和 B 是纯 L2 的活，做完 M1 就完整了。**
