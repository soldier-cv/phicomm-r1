## 1. 设备事实（都是实测，决定架构约束）

| 事实 | 数值 | 对架构的约束 |
|---|---|---|
| 内存 | 490 MB 总，**空闲 5.7 MB** | ❗设备上不能跑 Web 服务、不能跑数据库、不能常驻多进程 |
| `/data` | 988 MB，剩 708 MB | 够放一两个自己的 App |
| 屏幕 | 有（能截到图），目前显示 MOD 的测试页 | 可以做界面，但**不是主交互面**——主交互是语音 |
| 身份 | 无 root，SELinux Enforcing，uid 恒定 2000(shell) | 改不了系统分区，只能装 App |
| 系统私有服务 | `FXSystemPrivate: [android.os.ISysPrivate]` 存在 | 灯环/系统模式的唯一入口，**要进程身份** |
| 装包入口 | adb 5555 局域网敞开 | 可用于部署，但**不能当运行时依赖** |

## 2. 最重要的那条线：谁需要什么身份

```
┌─────────────────────────────────────────────────────────────┐
│  需要「原厂包身份」的能力（普通 App 拿不到）                    │
│  ─ 灯环 24 位 / 休眠灯 / 网络灯       (ISysPrivate msgcenter) │
│  ─ 系统模式 setSysMode                 (ISysPrivate)          │
│  ─ 原厂唤醒词 + ASR 链路               (云知声 SDK 在包内)     │
│  ─ 四麦直开 /dev/snd 原始流            (platform_app 域)       │
│  ─ 播放控制 / DLNA / AirPlay           (player 包)             │
└─────────────────────────────────────────────────────────────┘
                          ▲
                          │ 只能通过「顶替原厂包」获得
                          │ （Janus，锁死包名）
┌─────────────────────────────────────────────────────────────┐
│  普通 App 就能做的                                             │
│  ─ 网络请求 / 自己的 UI / 自己的播放器                          │
│  ─ AudioRecord 录音（可能已含四麦增强，待验证）                 │
│  ─ 局域网 HTTP 服务（**但内存不够，不要做**）                   │
└─────────────────────────────────────────────────────────────┘
```

**这张图就是整个架构的根**：能力分两半，一半要身份，一半不要。
设计的关键在于**怎么让「不要身份」的那半承担尽可能多的东西**。

## 3. 推荐架构：三层，越往上越好改

```
┌───────────────────────────────────────────────────────────────┐
│ L3  控制面（跑在你自己的电脑 / NAS / 手机上，不占音箱内存）        │
│     - 配置界面、曲库、日志、刷机/打包                            │
│     - 通过局域网或 adb 与音箱通信                               │
└───────────────────────────────────────────────────────────────┘
                              ▲ HTTP / adb
┌───────────────────────────────────────────────────────────────┐
│ L2  业务 App（普通包名，如 com.yourname.r1）                     │
│     - 全部业务逻辑：对话、意图、音乐、消息                       │
│     - 自己的配置（SharedPreferences）                           │
│     - 要调底层的部分，JS bridge / 广播 / 本地 socket 到 L1 桥    │
│     - ✅ 随时 pm uninstall，不影响原厂                            │
└───────────────────────────────────────────────────────────────┘
                              ▲ Binder / 广播 / socket
┌───────────────────────────────────────────────────────────────┐
│ L1  桥（顶替 device 包的那个壳，尽量薄）                          │
│     - 只做「转发」：把原厂唤醒结果、IPC 能力暴露给 L2            │
│     - 持有 ISysPrivate 连接（灯环、系统模式）                    │
│     - 原厂云知声 SDK 继续跑（唤醒/ASR 不用自己实现）             │
│     - ⚠️ 这一层一旦坏了，语音助手就没了 → 必须能回退               │
└───────────────────────────────────────────────────────────────┘
```

### 为什么这样分

| 关注点 | 解决方式 |
|---|---|
| 我们要不断改功能 | 全在 L2，改完 `pm install` 就行，**不用重新 Janus 打包** |
| 内存只有 5.7MB | L1 尽量薄（几百行），L2 单进程，L3 不在设备上 |
| 怕搞坏 | L1 只用原厂已有的能力，不碰系统分区；回退 = `pm uninstall` + 恢复原厂包 |
| 能力难拿 | 只把真正需要身份的东西放进 L1，其余全在 L2 |

## 4. L1 桥的候选实现方式（待选）

| 方式 | 优点 | 缺点 |
|---|---|---|
| **A. Janus 换掉 device 包** | 能拿到全部能力 | 锁包名，要重新打包才能改，有风险 |
| **B. 反射 + 同进程** | 不用换包 | 进不了特权域，灯环拿不到 |
| **C. 广播 / 本地 socket 中转** | 解耦干净 | 又要多一个服务，内存紧张 |
| **D. 什么都不做，只用 AudioRecord + 自己 ASR** | 最干净 | 丢掉原厂唤醒和灯环 |

> 我的倾向：**先按 D 起步做 L2（验证业务），等业务跑通了再决定 L1 要不要做**。
> 因为引用文档里有个关键待验证点：**四麦算法可能已经在 Audio HAL 里**，
> 如果普通 `AudioRecord` 就能拿到增强音频，那 L1 的必要性就大幅降低。

## 5. 开发与部署流程

```
   改 L2 代码
       │
       ├─ 本地编译成 apk
       │
       ├─ [可选] 在 AOSP armv7 模拟器（API 22）跑一遍
       │
       └─ 推到音箱
              ├─ 方式1: adb install（快，但依赖 5555 开着）
              ├─ 方式2: 放 Web 服务器上，音箱自己下载安装（不依赖 adb）
              └─ 方式3: L3 控制面里点一下
```

**建议**：把 apk 放在 L3 的 Web 服务器上，音箱上一个"检查更新"按钮——
这样**即使哪天 5555 被关了，也还能升级自己的 App**。

## 6. 风险与回退

| 风险 | 影响 | 回退 |
|---|---|---|
| L1 桥装坏 | 语音助手没了 | `pm uninstall com.phicomm.speaker.device` → 回 `/system/app/Unisound` |
| L2 业务 App 崩 | 只有它自己崩 | `pm uninstall com.yourname.r1` |
| IP 变了 | adb / 网页都找不到 | 路由器绑 MAC（`<音箱MAC>`） |
| 5555 被关 | 不能再 adb 部署 | 走 L3 网页下载安装 |
| `/data` 写满 | 系统不正常 | 708MB 余量，够；别往设备上存媒体 |
