# 功能设计（基于实测的内部能力）

> 原则：**先列清楚这台机器到底能做什么，再决定做什么。**
> 每个功能都标：谁来做（L1/L2）、依赖什么、优先级、当前状态。

## 一、能力清单（实测过的内部 API）

| # | 能力 | 实现方式 | 谁能用 | 状态 |
|---|---|---|---|---|
| C1 | 唤醒词「小讯小讯」 | 云知声 SDK（在 device 包内） | 只有 device 包 | ✅ 能用 |
| C2 | 本地 ASR | 云知声（离线） | 只有 device 包 | ✅ 能用 |
| C3 | 麦克风采集 | card1 直开 ALSA（被独占） | 只有 device 包 | ✅ 但独占 |
| C4 | 灯环 24 位 | `ISysPrivate` / `MessageDispatchManager` 4096 消息 | 需 device 包身份 | ✅ 服务存在 |
| C5 | 系统模式 | `ISysPrivate.setSysMode` | 需 device 包身份 | ⚠️ 取值待测 |
| C6 | 原厂 TTS | `libyzstts.so` | 只有 device 包 | ✅ 能用（音质一般） |
| C7 | 播放控制 | `com.phicomm.speaker.player`（4 个子进程常驻） | player 包 | ✅ 能用 |
| C8 | DLNA 接收 | 同上 `:DlnaPlayer` | player 包 | ⚠️ **进程在，但没在广播** |
| C9 | AirPlay 接收 | `:AirPlayer` + `airskill` | player + airskill | ⚠️ 同上 |
| C10 | 蓝牙 A2DP | 蓝牙栈已配好 | 普通 App 也能 | ✅ 实测已配对 |
| C11 | 音量控制 | `AudioManager` | **普通 App 就能** | ✅ |
| C12 | 按键（单击/长按/三击） | `/dev/input` + 原厂 keyevent 框架 | 需 device 包身份 | ⚠️ 待接 |
| C13 | 设备屏幕 | Activity 全屏绘制 | 普通 App | ✅ 能显示 |
| C14 | 配网 | `com.phicomm.speaker.netctl` | 系统包 | ⚠️ 未摸 |
| C15 | 网络请求 | 普通 HTTP | **普通 App** | ✅ |
| C16 | 定时/闹钟 | 自己做，`AlarmManager` | **普通 App** | ✅ |
| C17 | 内存/存储状态 | 读 `/proc` | **普通 App** | ✅ |

## 二、DLNA 到底能不能用（单独说清楚）

### 实测到的事实

```
ps:  com.phicomm.speaker.player
     com.phicomm.speaker.player:NetPlayer
     com.phicomm.speaker.player:DlnaPlayer     ← DLNA 栈在跑
     com.phicomm.speaker.player:AirPlayer      ← AirPlay 栈在跑
     com.phicomm.speaker.airskill

/proc/net/udp:  没有 1900(0x076C) 的绑定
                → 没有在 SSDP 上广播，所以手机上的投屏列表里看不到它
```

从 PC 发 SSDP M-SEARCH 到 255.255.255.250:1900，**没有任何设备回应**（整个局域网都没有）。

### 结论

**DLNA 的代码在里面，但没被激活。**

对照 P2（XiaoZhi）的补丁清单，他们专门写了 `patch_dlna_sync.py`（同步"正在播放"）和
`patch_seek.py`，说明 DLNA 在 R1 上是**存在但要激活/修补**的。

### 怎么才能用上

三条路，按可行性排：

| 方案 | 做法 | 难度 |
|---|---|---|
| **A. 让 player 进入 DLNA 模式** | 反编译 `com.phicomm.speaker.player`（1.1 MB，很小），找它的启动入口/广播 | 中（L1 范畴） |
| B. 自己写一个 DLNA 渲染器 | 需要 SSDP + UPnP AVTransport + HTTP 取流 | **高**，8 MB 内存扛不住 |
| C. 用蓝牙代替 | 已经能用（C10） | 零成本 |

> **建议**：第一期先用**蓝牙**（现在就能用），DLNA 留到 L1 阶段再挖——
> 因为 DLNA 的进程属于 player 包，动它等于第二个 Janus 顶替，成本不低。

## 三、功能清单（按优先级）

### P0 · 没有就不能用

| 功能 | 谁做 | 依赖 | 状态 |

| 音量加减 | L2 | `AudioManager` | ⬜ |

| 功能 | 谁做 | 依赖 | 说明 |
|---|---|---|---|

| 唤醒词查看 | L1 | C1 | 只读 |
| 投屏接收（DLNA/AirPlay） | L1 | C8/C9 | 见第二节 |
| 快捷指令短语（"关灯"→ 场景） | L2 | 意图路由 | 纯软件 |

### P2 · 锦上添花

| 功能 | 说明 |
|---|---|
| Home Assistant 接入 | 一句话控制全屋设备 |

| 按键自定义 | 单击/双击/长按绑定不同动作（需 L1） |

| 语音播报天气/新闻/待办 | LLM + 外部 API |

## 四、操作便捷性（比功能更重要）

现役那个页面最大的问题是"能用但难用"。我们的做法：

### 4.1 进入方式

| 方式 | 做法 | 成本 |
|---|---|---|
| **手机浏览器加桌面图标**（PWA） | 加 `manifest.json` + 图标，安卓浏览器可"添加到主屏" | 低，**推荐** |
| 扫码直开 | 打一张二维码贴纸贴音箱底下 | 极低 |
| 固定域名 | 路由器绑 IP + 局域网 DNS，记 `r1.local` | 中 |
| 微信/浏览器书签 | —— | 零 |

### 4.2 常用操作一屏可达

```
首页（打开就是）
├ 正在播放（大卡片，直接能按）
├ 四个快捷（氛围灯/音量/蓝牙/休眠）
└ 对话输入框（不用切页就能说话）
```

**对比现役页面**：要找"开个灯"得点两次（先进标签页，再点按钮），
而且不知道灯现在是什么状态。

### 4.3 每个动作都要有回执

- 开关类：按钮本身变亮/变暗 + 一行小字"已生效 · 刚刚"
- 长操作（播报、搜索）：进度条 + 可取消
- 失败：显示设备返回的原始错误 + 一个"重试"按钮

### 4.4 语音也能做同样的事

界面上有的动作，尽量也给一句语音指令：

| 界面操作 | 语音说法 |
|---|---|
| 音量 40 | "声音大一点" / "音量调到 40" |
| 氛围灯 | "开个氛围灯" |
| 播放 | "放一首周杰伦" |
| 定时 | "明早七点叫我" |
| 休眠 | "你先睡吧" |

> 这条是"便捷性"的核心：**开着音箱的时候，人是不想掏手机的。**

### 4.5 危险操作的隔离

现役页面的 `/qw_pubkey?gen=1` 会直接覆盖私钥文件，按钮就在普通表单里。
我们的做法：

- 危险操作（清空配置、重启设备、卸载）统一放进「设置 → 高级」，**默认折叠**
- 每个都要二次确认，确认框里写清"会发生什么"
- 操作后给一个"撤销"窗口（能做就做）

## 五、功能与架构的对应

```
L1（Janus 顶替）        L2（普通 App）              L3（可选）
├ 唤醒 / ASR            ├ 对话 / LLM                ├ 日志归档
├ TTS（备用）           ├ TTS（HTTP 自播）           ├ 升级分发
├ 灯环                  ├ 音乐 / 播放器              └ 远程入口（延后）
├ 系统模式              ├ 定时任务
├ 拆闸门                ├ 配置界面（8686）
└ 投屏接收（DLNA）       ├ 状态 / 日志
                        └ 意图路由
```

**判断规则**：需要**设备身份**的 → L1；纯软件/网络 → L2；不常变 → L1，天天变 → L2。
