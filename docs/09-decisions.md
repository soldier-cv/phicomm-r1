# 决策记录（ADR）

> 每条决策写清楚：**背景 → 选项 → 决定 → 理由 → 证据**。
> 要推翻某条之前，先读它的证据；证据不够就补实验，别凭感觉改。

## D-01 · 项目定位：重做一个 App，而不是改别人的

**背景**：现役 `unisound_MOD_v1.0.4` 能用，但闭源、无鉴权、主页是测试页。

**选项**
1. 反编译它的前置 DEX，改一改再用
2. 从零做自己的
3. 继续凑合用

**决定**：**2，从零做**。

**理由**
- 改别人的 DEX 等于继承他的全部技术债，且每次升级都要重做一遍反编译。
- 我们要的东西（可远程、可迭代、有配置界面）和它的形态不一致。

**证据**：`archive/where-8080-comes-from.md`（它是什么）、`archive/webui-8080-api.md`（它的接口清单）。

## D-02 · 一定走 Janus 顶替，而不是"新包名拿权限"

**背景**：想在设备上拿到特权能力。

**选项**
1. 换个包名，靠 `sharedUserId` / `seinfo` 提权
2. 伪造签名
3. Janus（CVE-2017-13156）顶替原厂包

**决定**：**3**。

**理由**
- 1 ❌ `seapp_contexts` 里没有任何 `name=` 规则，**包名对 SELinux 域零影响**。
- 2 ❌ 平台私钥在斐讯手里；`mac_permissions.xml` 只认一把证书（`34:A2:D2:FE:…`）。
- 3 ✅ 本机现役包就是 Janus，**已证明可行**；且不需要 root。

**代价**：包名被锁死为 `com.phicomm.speaker.device`。

**证据**：`archive/correction-janus-not-resign.md`（我自己实测的文件布局）、
`archive/ecosystem-research.md` §3.3（seapp_contexts / mac_permissions 的原文）。

## D-03 · 拆成 L1 + L2 两层

**背景**：Janus 顶替一旦定了，所有代码都会被锁进那个包，改一次就要重打包。

**选项**
1. 全部塞进 L1（P1/P2 的做法）
2. 全部放外部 App（P3 的做法）
3. 能力留 L1，业务放 L2

**决定**：**3**。

**理由**
- 1 ❌ 每次改业务都要重新 Janus 打包，迭代成本不可接受。
- 2 ❌ 外部 App 拿不到灯环、麦克风、语义，能力残缺（P3 的 `/led-color` 是空的）。
- 3 ✅ 90% 工作量在 L2，普通 `pm install` 就能更新，而且随时能卸载回退。

**证据**：`archive/project-comparison.md` §3.2（五条约束的满足度）、§5.2。

## D-04 · 麦克风：不自己采，用原厂的识别结果

**背景**：一开始以为"普通 App 用 AudioRecord 就能采四麦"。

**选项**
1. L2 自己采（`AudioRecord`）
2. 停掉原厂链，自己做唤醒 + 采音
3. 用原厂的 ASR 结果，不碰麦克风

**决定**：**3**。

**理由**
- 1 ❌ **实测否定**：`subdevices_count: 1`，被原厂链 100% 独占；
  L2 能初始化、能 `startRecording`，但 `read()` 永远阻塞、0 采样。
- 2 ❌ 清理后可用约 25MB，跑唤醒引擎仍太紧；唤醒质量要从零调。
- 3 ✅ 唤醒 + ASR 是原厂出厂调好的，白拿。

**证据**：`archive/evidence-mic-exclusivity.md`（三组对照实验的数据）。

> ⚠️ 这条是**整个架构的地基**。如果将来有人想推翻，必须重新做那个对照实验。

## D-05 · 8080 不复用，另起端口

**决定**：新接口用 `8686`，不兼容旧的 8080。

**理由**
- 8080 是现役 MOD 的私有实现，无鉴权、裸 GET、`/qw_pubkey?gen=1` 能覆盖私钥。
- 原厂从来没有 8080，**没有任何兼容包袱**。

**证据**：`archive/where-8080-comes-from.md`、`archive/webui-8080-api.md`。

## D-06 · 单一入口：远程只访问 L2

**决定**：所有对外 HTTP 都进 L2；L1 不监听任何端口，只接受 L2 的桥消息。

**理由**
- 一个鉴权点、一套日志、一个地址。
- L1 可以保持极薄；以后换 L1 实现不影响外部。
- 现在的 8080 就是"直接暴露设备能力"的反面教材。

**证据**：`08-http-api.md` §2。

## D-07 · 桥协议用广播 + JSON，不用 AIDL

**决定**：L1↔L2 用 `Broadcast` 传 JSON（单 action + `d` extra）。

**理由**
- 两边签名不同（L1 是原厂证书、L2 是我们的），**用不了 signature 级权限**，
  所以鉴权靠"包名 + 证书指纹比对"。
- 广播在 Android 5.1 上隐式限制少，实现最省事，不需要两边共享 AIDL 文件。
- 请求/响应靠 `msgId` 关联（L1 回一条带同 id 的广播）。

**替代方案**（如果要低延迟/大流量再换）
- 本地 socket（抽象命名空间）：更快，但跨 uid 传密钥麻烦。
- ContentProvider `call()`：天然的请求/响应，但要加 Provider。

**证据**：`07-protocol.md` §2。

## D-08 · 部署不依赖 adb

**决定**：L2 的更新走「L3 网页上传 → 推给 L2 → 自安装」，adb 只用于开发期。

**理由**
- adbd 一周内挂死两次（只能断电恢复）。
- 一旦 adb 不可用，如果升级也依赖它，就彻底失联。

**证据**：`11-troubleshooting.md` 第 1 节与第 8 节。

## D-09 · 先只做局域网；远程（ZeroTier 跳板）延后

**决定**：第一期**只做局域网**。远程访问用「一台同时接入 ZeroTier 和家里局域网的机器做跳板」，
但**不列入第一期范围**。

**理由**
- 局域网覆盖 95% 的使用场景（在家用手机控制）。
- 跳板涉及另一台机器的转发/路由，是独立小工程，不该拖累主线。
- L2 只需要监听本地 8686，跳板以后加在它前面，**L2 一行都不用改**。

**跳板方案的要点（已想清楚，先记着）**
- 不用改路由器、不用公网 IP、不做端口映射。
- 电脑上 ZeroTier 已经装好（实测 `ZeroTier One` → `100.64.0.110`）。
- 到时候在那台机器上做个反向代理指向 `<音箱IP>:8686` 即可。

**为什么 ZeroTier 不能直接装音箱**：Android 5.1 / armv7 / 清理后可用约 25MB 内存。

**证据**：`08-http-api.md` §3.0 / §3.2。

## D-12 · TTS：L2 走 HTTP 拿音频自己播，不依赖原厂 TTS

**背景**：实测这台机器**没有系统 TTS 引擎**（`TextToSpeech.onInit` 返回 `status=-1`），
原计划「L2 用系统 TTS 播报」作废。

> 📌 **2026-10-29 修订**：最初据此写下「TTS 必须由 L1 提供」。用户指出原厂云知声 TTS
> 用起来并不好，而且可以**本地装一个 TTS 服务（HTTP API）**或用云 TTS。据此修订本决定。

**决定**：**L2 自己完成播报** —— 向可配置的 TTS 端点请求音频字节流，用 `MediaPlayer` 播放。
TTS 端点三种形态都支持：

| 形态 | 例子 | 请求 |
|---|---|---|
| **本地 TTS 服务** | 局域网自建的 GPT-SoVITS / edge-tts / 其它 HTTP TTS | `POST {baseUrl}` → 返回 audio/* |
| **OpenAI 兼容** | `{base}/audio/speech` | `POST` JSON → 返回 mp3 |
| **云厂商** | 火山/豆包、Azure | 各自协议，封装成同一种内部接口 |

**理由**
- 本机没有系统 TTS，但**播放在设备上是通的**（AudioFlinger 正常，原厂 TTS 播放也走它）。
- 本地 TTS 服务音色可换、可离线，比原厂机械音好，而且不占设备内存（跑在别的机器上）。
- 这样 L1 就不必承担播报职责，`SPEAK` 从「唯一出声路径」降级为「备用/原厂兜底」。

**推论（重要，推翻了上一版结论）**
> **L1 做出来之前，L2 也能出声** —— 只要配好 TTS 端点。
> 第一期的验收可以恢复成「音箱真的开口说话」。

**待验证**：普通 App 的 `MediaPlayer` 在这台机器上能否正常出声（O-14）。

**证据**：`archive/evidence-l2-skeleton.md` §2.2。

## D-13 · 定时任务归 L2，不用原厂的闹钟

**背景**：R1 原生有云知声的备忘/提醒能力（`MemoDB.db` + `MemoRingingService`），
`localmemo` 表结构完整（内容、重复、贪睡、铃声）。

**决定**：**L2 用 `AlarmManager` 自己做**，不碰 `MemoDB.db`，也不用 MOD 的 `/alarm_*`。

**理由**
1. 原厂提醒的入口是云知声 **NLU 意图**（云端已下线），语音根本到不了它；
2. 直接写 `MemoDB.db` 有风险——`MemoRingingService` 在内存里缓存状态，背后改库不保证生效；
3. 原厂 schema 只能表达"响铃"，而我们需要"播报/放歌/场景/音量/灯"；
4. MOD 那套是别人的实现，L1 替换后就没了；
5. `AlarmManager` 是系统级的，`dumpsys alarm` 实测系统自己就在用 `RTC_WAKEUP`，
   而且 5.1 没有 Doze，`setExact` 准点。

**附带发现（影响实现）**
- **ROM 里没有任何铃声文件**（`/system/media/audio` 都不存在）→ 闹钟必须有内置兜底音 `chime.wav`。
- 系统里没有独立闹钟 App。

**证据**：`06-scheduler.md` 第一节。

## D-14 · 运维中枢通过本地回环 ADB (127.0.0.1:5555) 穿透特权操作

**背景**：
音箱物理内存仅 512MB（清理后空闲约 25MB），用户需要清理废弃应用回收内存、安装新应用、以及在日常更新时免插线升级。
但普通非系统 App（`com.r1.brain`，无 platform 签名）没有系统权限，直接调用 `pm install`、`pm uninstall`、`am force-stop`、`reboot` 会直接报 `SecurityException`。

**选项**：
1. 要求设备必须 root 并在 App 内执行 `su`。
2. 依赖外部电脑反复用 USB/Wi-Fi 执行 `adb`。
3. 利用音箱本地回环网络连接自身的 `adbd` 守护进程（`127.0.0.1:5555`）执行命令。

**决定**：**3，纯 Java 实现原生 TCP ADB 协议客户端连接 `127.0.0.1:5555`**。

**理由**：
- R1 原厂固件 `adbd` 监听在 `0.0.0.0:5555`，且未启用 ADB 身份鉴权密钥（免认证）。
- 通过纯 Java 原生 Socket 发送标准的二进制 ADB 数据包（`CNXN` 握手 → `OPEN` 打开 shell 流 → `WRTE`/`OKAY`/`CLSE` 读取输出），App 可瞬间以 `shell` (uid=2000) 身份执行特权指令。
- 免 root、免平台签名，即可完成静默安装、卸载应用、强停进程和硬件系统重启。

**证据**：`DeviceOps.java` 实测与 `archive/adb-protocol` 验证。

## D-15 · 极低内存纯流式 APK 上传机制（杜绝 512MB RAM OOM）

**背景**：
用户通过 Web 控制台上传 `.apk` 安装包或升级包，体积通常在 5MB ~ 30MB 之间。
R1 物理内存 512MB（实际 490MB），原厂后台常驻后空闲内存仅约 10MB ~ 25MB。

**选项**：
1. 采用常规 HTTP 框架一次性将请求体全部读入 `byte[]`。
2. 引入第三方 Apache Commons FileUpload / Multipart 解析库。
3. 纯流式传输：跳过全量请求体缓冲，用 8KB 循环缓冲区将 Socket InputStream 直写至临时磁盘 `/data/local/tmp`。

**决定**：**3，极低内存纯流式直写机制**。

**理由**：
- 选项 1 必然导致瞬间申请 10~30MB 堆内存，直接引发 OOM 或严重 GC 停顿卡死。
- 选项 2 会引入多余的外部依赖，违背“零第三方重库依赖、纯原生 Android SDK 手写”的架构约束。
- 选项 3 无论上传多大的 APK 文件（哪怕 50MB），进程内内存常驻开销严格锁死在 **64KB 以内**，平滑安全。

**证据**：`HttpServer.java` `/api/v1/apps/install` 路由实现。

## D-16 · 免 Key 开放源 + 和风天气双通道自适应降级

**背景**：
原设计与原型仅对接和风天气，需要用户自行申请商业/个人 API Key 并填写配置。如果未配置 Key，天气查询直接不可用，使用门槛高。

**选项**：
1. 强制要求用户必须配置和风天气 Key。
2. 纯走大模型闲聊生成天气（不可靠、易产生幻觉且耗费大模型 Token）。
3. 引入免 Key 的开放气象源（基于 wttr.in），并与和风天气组成双通道自适应降级体系。

**决定**：**3**。

**理由**：
- 默认无需配置任何 Key，即可根据当前城市（或自动提取的城市）直接播报实时天气状况、气温、风向风力与相对湿度，做到真正开箱即用。
- 用户若配置了和风天气 Key，则优先调用官方通道；官方通道一旦不可用或超时，自动无缝降级至免 Key 开放源，永不中断。

**证据**：`WeatherService.java` 实现。

## D-19 · 思考控制只发 `reasoning_effort`，用一档设置覆盖两种需求

**背景**：在用的两个模型（`free/ouyi-5-preview`、`plan/deepseek-flash`）都是推理型：
先花看不见的"思考 token"再写正文，两者共用同一份 `max_tokens`。
设备上 `maxTokens=256` 时，复杂问题会把 256 全用在思考上，正文为空（`finish_reason=length`），
用户看到的是"大模型响应内容为空 + 请检查 API Key / 网络"——**方向完全是错的**。

**选项**
1. 只把 `max_tokens` 调大
2. 按各家私有字段分别适配（`thinking` / `enable_thinking` / `thinking_budget`）
3. 统一用 OpenAI 兼容的 `reasoning_effort`，设置页给"自动 / 关闭 / 低 / 中 / 高"一档

**决定**：**3**，**默认档位为「关闭」**，另加两条兜底：
- 档位可能产生思考 token 时，额外补 1024 输出额度（关闭档不补）；
- 上游以 400 拒绝 `reasoning_effort` 时，去掉该字段重发一次，别让"思考设置"把能用的模型弄挂。

**理由与证据**（2026-11-01 在 `<服务IP>:8317` 实测，同一提示词、同一预算）

| 请求字段 | `plan/deepseek-flash` | `free/ouyi-5-preview` |
|---|---|---|
| `reasoning_effort: none` | 思考 243 → **0**，4.7s → 2.0s | 思考 20 → **0** |
| `thinking.type` | 被忽略 | **HTTP 400 Unknown parameter** |
| `enable_thinking` | 被忽略 | **HTTP 400 Unknown parameter** |
| `thinking_budget` / `chat_template_kwargs` | 被忽略 | 被忽略 |

- 2 ❌ 私有字段互相排斥：**同一个网关里两个上游**，发 `thinking` 会直接打死其中一个，
  等于把"换个模型"变成"改一次代码"。
- 3 ✅ DeepSeek 官方文档：`reasoning_effort` 取 `none` 关闭思考、`low/high/max` 开启，
  `minimal` 视作 `low`、`medium`/`xhigh` 视作 `high`；OpenAI 系模型也认这个字段。
- "模型是否支持思考"不单独做开关：不支持思考的模型本来就没有思考 token，选"自动"即可；
  多一个开关只多一种配错的可能。
- 默认给"关闭"：思考 token 与正文抢同一份预算，关掉最不容易出"空回复"；
  实测（`plan/deepseek-flash`、256 预算、6 条真实问句）思考归零、2.3~3.4s、
  回答 50~80 字且全部 `finish=stop`，没有截断。

**代价**：`medium` 在 DeepSeek 上等价于 `high`；"关闭"之后 `maxTokens` 是正文硬上限，
问题特别长时仍会被截断，想要长回答要同时调大它。

**证据**：`ReasoningEffort.java`（档位与协议值）、`Brain.emptyReplyMessage`（空回复文案）、
本次实测记录（见上表）。

## D-20（候选，未定）· 每条指令都交给大模型做分发？

**提议**：把 ASR 文本先发给大模型，由模型判断意图、给出动作与参数，本地只负责执行。

**现状**：`IntentRouter` 先跑本地规则（灯环 / 音量 / 播控 / 点歌 / 闹钟 / 天气……），
命中就执行（实测 3~10ms）；未命中的才把原话 + 最近 3 轮历史发给大模型，
而**模型只产出话术，不产生动作**。

**为什么值得做**：长尾表达现在等于没有能力。「来点适合睡觉的」「放首刚火的那个」这类
本地规则覆盖不到，落到模型只能得到一段安慰话。让模型选工具，能一次解决一大片。

**代价（这台机器的硬约束）**：

| 项 | 数字 |
|---|---|
| 网络往返 | 实测 0.5~3s（本地意图 3~10ms），用户能感知到"卡了一下" |
| 断网 | 直接失能；本地意图完全不受影响 |
| 幻觉 | 模型会调用设备没有的能力（"打开空调"），必须由本地白名单兜住 |
| 内存/CPU | 512MB、单核，不可能跑本地模型，只能走局域网网关 |

**建议的折中（等用户拍板再做）**：

1. 高频、低时延、动作固定的继续走本地：音量大/小、暂停/继续、灯环、闹钟。
2. 其余统一交给模型的**工具调用**（function calling）：给模型一份能力清单
   （`{name, 参数, 一句描述}`，与 `docs/08` 的接口一一对应），模型只能从清单里选，
   本地按名字白名单执行，失败回落到话术。
3. 工具清单就放在 L2 内存里生成，不引入 MCP 这类外部协议——
   模型和音箱之间只差一个 `tools` 数组，多一层协议只会增加故障面。
4. 先做灰度开关（设置页「智能分发」），默认关，出问题一键回退到纯本地意图。

**判据**：如果 20 条真实语音里有 5 条以上是本地规则覆盖不了的表达，就值得做；
否则优先补本地规则（成本低一个数量级）。

**候选实现：TypeSafe Jev（2026-11 调研）**。它是「给状态、问选择题、回带概率的答案」这一类模型，
不生成文本，正适合做上面的「选工具 + 填参数」；官方 smart-home demo 就是我们这个场景
（判定为设备指令就本地执行，判定为闲聊才交 LLM）。成本可忽略（\$0.042/Mtok 输入，输出免费）。
两个门槛必须先过：① 文档明说英语最准、CJK 只保证「能处理」，**必须用我们自己的语料实测**；
② 它是公有云 `api.typesafe.ai`，端到端受跨境 RTT 支配——我们现在的 LLM 走局域网网关，
这一段省不掉。三条都满足才动手：中文准确率 ≥90%、端到端 <1s、断网时能退回本地规则。

## D-21（候选，未定）· 对话节奏：从「一问一答」走向「判停 + 打断」

**现状**：唤醒词门控 → 固定窗口录音（10 秒上限）→ 整段上传 ASR（约 5 秒，冷启动 11 秒）→ LLM（0.5~3 秒）→ TTS。
首响 6~8 秒，播报时不听，用户要打断只能等。**这不是"对话"，是"一问一答的查询机"。**

**正解（豆包路线，可查）**：2025-01 端到端 S2S 取代级联 → 2026-04 Seeduplex 全双工（边听边说）→ 2026-08 SeedRealtime。
关键不是模型多大，而是四件事：动态判停（声学+语义，不是固定静音）、随时打断、流式（20ms 一包音频 / 边出字边合成）、
执行结果回灌给模型。官方口径：判停延迟 -250ms、抢话比例 -40%、误回复/误打断减半。

**我们能补的（按性价比）**：

| 优先级 | 做什么 | 为什么划算 |
|---|---|---|
| P0 | 打断：播报时继续 tee，检测到人声立刻停 TTS | 体验差别最大，纯本地判断，不依赖网关 |
| P0 | 判停：静音 700ms 且文本完整就收，别等满 10 秒 | 直接砍掉 2~5 秒等待 |
| P1 | 流式 ASR（网关侧 partial）→ 意图可提前命中 | 首响降到 1~2 秒 |
| P2 | 一次待确认状态机（pending_action），解决"嗯"这种确认 | 我们现在的"嗯"只能当没听清 |
| P3 | 端到端 S2S | 受限于麦克风被原厂独占，属于架构决策，不是优化 |
